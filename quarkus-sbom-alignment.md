# Quarkus SBOM Alignment with the Scanner Contract

Analysis of how Quarkus CycloneDX SBOM generation aligns with the
[SBOM Integration Contract](sbom-integration-contract.md) and what needs to change.

## Current Quarkus SBOM Output

Quarkus generates two distinct kinds of SBOMs for packaged applications:

### External (package-level) SBOM

Generated by `CycloneDxProcessor.generate()` whenever `quarkus.cyclonedx.enabled=true`
(the default). One SBOM is produced per packaged artifact (fast-jar, mutable-jar, uber-jar,
native image). It records the full distribution layout including evidence/occurrence paths.

| Package type | Current output location | Current filename |
|---|---|---|
| fast-jar | `target/` | `quarkus-run-cyclonedx.json` |
| mutable-jar | `target/` | `quarkus-run-cyclonedx.json` |
| uber-jar | `target/` | `myapp-runner-cyclonedx.json` |
| native | `target/` | `myapp-runner-cyclonedx.json` |

### Embedded SBOM

Generated by `CycloneDxProcessor.generateEmbeddedSbom()` when
`quarkus.cyclonedx.embedded.enabled=true` (or when the `/.well-known/sbom` endpoint is
enabled). Describes the Maven dependency graph without distribution path information.

| Package type | Embedded in | Resource path (default) |
|---|---|---|
| fast-jar | `quarkus/generated-bytecode.jar` | `META-INF/sbom/dependency.cdx.json.gz` |
| mutable-jar | `quarkus/generated-bytecode.jar` | `META-INF/sbom/dependency.cdx.json.gz` |
| uber-jar | runner JAR directly | `META-INF/sbom/dependency.cdx.json.gz` |
| native | GraalVM `sbom` / `sbom_length` symbols | n/a (GraalVM handles this) |

## Issues and Required Changes

### 1. External SBOM filename does not conform to the contract (§3.1)

**Contract:** scanners MUST recognize `*.cdx.json` files. Generators MUST use the `*.cdx.json`
pattern. Generators SHOULD default to `sbom.cdx.json` for directory distributions.

**Current:** Quarkus uses `<name>-cyclonedx.json` — scanners following the contract will not
recognize these files.

**Required changes:**

- **Fast-jar / mutable-jar** (directory-based distribution): rename to `sbom.cdx.json`
  at the distribution root.
- **Uber-jar** (JAR with external SBOM): rename to `<runner-filename>.cdx.json` next to
  the runner (e.g., `myapp-runner.jar.cdx.json`).
- **Implementation:** add `standardNaming` and `directoryDistribution` flags to
  `CycloneDxSbomGenerator`; update `toSbomFileName()` accordingly.

---

### 2. External SBOM placement for fast-jar / mutable-jar (§3.2)

**Contract:** directory-based distributions MUST place the SBOM at the distribution root.

**Current:** placed in `target/` (the Maven build output directory). The distribution root
for fast-jar is `target/quarkus-app/`, so the SBOM ends up one level above it.

**Consequence:** occurrence paths in the SBOM (e.g., `lib/main/netty-buffer.jar`) are
relative to `target/quarkus-app/`, but the SBOM file itself is in `target/`. A scanner
resolving occurrences relative to the SBOM location gets the wrong paths.

**Required change:** write the SBOM to the distribution directory. This is a **breaking
change** for anyone relying on the current location.

**Migration:** introduce `quarkus.cyclonedx.legacy-placement` (default `false`).
When `true`, retains the old behavior.

**Implementation:** expose `getDistributionDirectory()` from `CoreSbomContributionConfig`.
In `CycloneDxProcessor.generate()`:

```
isDirectoryDist = manifestConfig.getDistributionDirectory() != null

outputDir = legacyPlacement  ? outputTarget.getOutputDirectory()       // target/  (old)
          : isDirectoryDist  ? manifestConfig.getDistributionDirectory() // target/quarkus-app/
                             : artifactResult.getPath().getParent()     // target/ (next to uber runner)
```

---

### 3. External SBOM placement for uber-jar (§3.2)

**Contract:** `<jar-filename>.cdx.json` placed next to the JAR.

**Current:** placed in the correct directory (`target/`), but with the wrong filename
(`myapp-runner-cyclonedx.json` instead of `myapp-runner.jar.cdx.json`).

**Required change:** rename only — directory is already correct.

---

### 4. Embedded SBOM: in `generated-bytecode.jar`, not `quarkus-run.jar`

For fast-jar and mutable-jar, the embedded SBOM is placed inside
`quarkus/generated-bytecode.jar` — an internal Quarkus infrastructure file. Its
`metadata.component` identifies the user's application (`pkg:maven/com.example/my-app@1.0.0`).

A scanner opening `generated-bytecode.jar` will find "my-app's SBOM" inside an internal
Quarkus file, which is semantically misleading.

The natural location would be `quarkus-run.jar` — the entry-point JAR that semantically
represents the packaged application. However, `quarkus-run.jar` is **not on the Quarkus
runtime classpath** (it is only the bootstrap launcher). Moving the SBOM there would
break the `/.well-known/sbom` endpoint, which loads the resource via
`getContextClassLoader().getResourceAsStream()` at startup.

**Options:**

| Option | Pros | Cons |
|---|---|---|
| Keep in `generated-bytecode.jar` | Endpoint works, no change needed | Semantically odd |
| Move to `quarkus-run.jar` | Semantically correct, entry-point JAR | Breaks endpoint (not on classpath) |
| Embed in both | Best of both worlds | Redundant, adds build complexity |
| Move to `quarkus-run.jar` + load by path | Semantically correct, endpoint works | More complex endpoint loading |

**Current recommendation:** keep in `generated-bytecode.jar` as a pragmatic choice.
Scanners will find it and correctly identify the app — the semantic oddness does not
affect correctness.

---

### 5. Embedded SBOM: no occurrence paths

The embedded SBOM is generated from `CurateOutcomeBuildItem` (the Maven dependency model)
without a distribution directory. This means no `evidence.occurrences` are populated —
components have no recorded file locations.

This is actually **intentional and correct**: the embedded SBOM lives inside
`generated-bytecode.jar`, which is itself nested inside the distribution. If occurrence
paths were added (e.g., `lib/main/netty-buffer.jar`), they would be relative to the
distribution root — but a scanner reading the embedded SBOM from inside the inner JAR has
no way to know the distribution root. Distribution-relative paths would be unresolvable
in that context.

**No change needed.** This is a known limitation worth documenting.

---

### 6. Embedded SBOM compression default

**Current:** compressed with GZIP by default (`META-INF/sbom/dependency.cdx.json.gz`).

**Problem:** `maven-assembly-sbom` (and likely other scanners) only recognize `*.cdx.json`
and `*.cdx.xml` — they silently miss `.cdx.json.gz`. Spring Boot does not compress either.

**Options:**

- Change the default to `compress=false` — breaking change for existing users.
- Update `maven-assembly-sbom` to handle `.gz` in embedded SBOMs.
- Do both.

---

### 7. Embedded SBOM path (already compliant)

**Contract (§3.3):** `META-INF/sbom/*.cdx.json`

**Current:** `META-INF/sbom/dependency.cdx.json` — already in the correct directory.

No change needed for the path structure.

## Summary Table

| Issue | Severity | Breaking? | Change type |
|---|---|---|---|
| External filename `*-cyclonedx.json` → `*.cdx.json` | High | Yes | Config + generator |

| Uber-jar filename rename only | Medium | Yes | Generator |
| Embedded SBOM in `generated-bytecode.jar` vs `quarkus-run.jar` | Low | No | Semantic only |
| No occurrences in embedded SBOM | Low | No | Intentional, document |
| Compression default breaks scanners | Medium | Yes (if changed) | Config default |
| Embedded path `META-INF/sbom/` | — | — | Already compliant |

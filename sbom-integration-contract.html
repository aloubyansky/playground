§2 The Challenge

A scanner is only as good as what it can identify

Vulnerability scanning depends on one thing: correctly identifying which product and which components are installed, then matching them against VEX/CVE data.

The traditional approach — inspecting the filesystem after the fact — cannot reliably answer either question. You can't match a CVE to a product you can't name, or to a library whose identity was erased at build time.

What's the product?

No universal convention exposes product name, version, or CPE on disk. Version files, manifests, directory names — or nothing at all. Every product does it differently.

What are the components?

Modern packaging deliberately dissolves component boundaries. The original coordinates a scanner needs are frequently gone by the time bytes hit the filesystem.

02 / 11
§2 Why filesystem scanning breaks

Packaging obscures component identity

Three techniques, ubiquitous in production builds, make components impossible to identify from files alone.

📦

Shaded / fat JARs

Many Maven artifacts repackaged into one JAR, often with relocated package names. The original GAV coordinates, directory structure, and manifest entries are lost.

✂️

Tree-shaking & minification

JS/frontend tooling removes unused code and compresses the rest. Package names, version strings, and file boundaries disappear.

⚙️

GraalVM native images

A single native binary compiled from Maven JARs, NPM packages, and more. No individual component files exist in the output at all.

The through-line: the information a scanner needs is available at build time and destroyed by packaging time. Reconstructing it afterward is guesswork.
03 / 11
Baseline The RPM layer

For RPM-based systems, part of this is already solved

Scanners don't start blind. On RPM-based systems (RHEL, Fedora) they read the RPM database — an authoritative record of what the package manager installed, and where each package came from.

How product identity is derived

local RPM DB (/var/lib/rpm) | +-- installed packages (name · version · release · vendor) | `-- originating repository `-- repository-to-cpe.json --> CPE --> VEX / CVE match

Clair, Trivy, and Grype enumerate installed RPMs/DEBs, resolve each package's repository to a CPE via a published mapping, then match against CPE-keyed security data. Reliable — and authoritative for whatever the package manager manages.

What it can't see

Bundled language deps

An RPM ships a fat JAR or WAR — the DB knows the one package, not the Maven/npm artifacts repackaged inside it.

Non-packaged distributions

WildFly, Keycloak, Artemis unpacked from a ZIP, or files added to a container via COPY — no DB entry ever exists.

Multi-product attribution

repo→CPE identifies the OS layer, not which application-level components belong to which upstream product.

The gap stays open. The package database is authoritative for OS-packaged content — but everything above it, the application and its language-ecosystem dependencies, is invisible to the package manager. That layer needs a different source of truth.
04 / 12
§2 SBOMs as the answer

Capture identity at build time, when it still exists

An SBOM generated during the build has the full dependency-resolution context — the dependency tree, resolved versions, licenses, and package identifiers.

That's exactly the information a scanner cannot reconstruct after packaging. So when an SBOM is present, it is the authoritative source of product and component identity — and scanners should prefer it over their own heuristics.

  • 01

    Explicit product identity

    Name, version, and CPE carried in a standard field — no guessing.

  • 02

    Complete component inventory

    Every component with a Package URL, even after shading or native compilation.

  • 03

    Authoritative, not heuristic

    Recorded from resolution truth, not inferred from bytes on disk.

§1 The Contract

Three parties, distinct obligations

Obligations throughout the contract are tagged with the responsible role and an RFC 2119 keyword: MUST SHOULD MAY.

Generator

SBOM tool developers
  • MUST Produce compliant SBOMs — structure, naming, placement.
  • MUST Identify components correctly.
  • SHOULD Support product-metadata configuration.

Product Team

Engineers configuring the product build
  • MUST Configure accurate identity (CPE, supplier, version).
  • MUST Ensure SBOMs ship in distribution artifacts.
  • SHOULD Choose the right output mode.

Scanner

Scanner developers & integrators
  • MUST Discover SBOMs & extract product/component info.
  • MUST Match against VEX/CVE sources.
  • SHOULD Follow external SBOM references.

These role chips recur on every slide that follows — each rule is tagged with who owes it.

§3 Placement & Naming

Where SBOMs live, how they're found

A discovery contract: predictable names and locations so scanners know exactly where to look. SBOMs MAY be GZip-compressed (.gz) in any location.

Generator
MUST use the *.cdx.json / *.cdx.xml pattern; SHOULD default to sbom.cdx.json.
GenProduct
MUST place the SBOM at the distribution root; external SBOMs sit next to the JAR as <jar>.cdx.json.
Generator
MUST embed SBOMs under META-INF/ inside JARs (Quarkus GZips by default).
Scanner
SHOULD read GraalVM native images via the exported sbom / sbom_length symbols (ELF · Mach-O · PE), then GZip-decompress.
Product Team
MAY attach SBOMs as OCI attestations (cosign / in-toto) or serve them at the RFC 9472 runtime endpoint /.well-known/sbom.

  bin/  kc.sh
  lib/  io.quarkus.quarkus-core-3.15.1.jar

  providers/

§4 · §5.1 SBOM Content — the single-product case

Product identity + component inventory

The straightforward model: one product, and every component belongs to it. Products like Keycloak and Artemis fit here directly.

Product Team MUST supply CPE, name, version in metadata.component. The CPE is the key that matches VEX/CVE data.

Generator MUST list every component with a purl; SHOULD add evidence/occurrences showing where each appears.

Scanner matches the product CPE against VEX and applies the result to all components in the SBOM.

This is the easy case. The next slides handle what happens when one CPE isn't enough.
sbom.cdx.json (single product){
  "metadata": {
    "component": {
      "type": "application",
      "name": "keycloak",
      "version": "26.0.0",
      "purl": "pkg:maven/org.keycloak/…@26.0.0",
      "cpe":  "cpe:2.3:a:redhat:keycloak:26.0.0:*:…",
      "supplier": { "name": "Red Hat" }
    }
  },
  "components": [
    { "name": "netty-buffer",
      "purl": "pkg:maven/io.netty/netty-buffer@4.1.115.Final",
      "evidence": { "occurrences": [
        { "location": "lib/netty-buffer-4.1.115.Final.jar" }
      ] } }
  ]
}

§4.3 External references

Following SBOMs into archives

SBOMs are usually self-contained — treat that as the norm. But a component MAY point to its own embedded SBOM via an externalReference of type bom. References are local only — remote URLs are out of scope.

Archive URI syntax

One syntax for occurrences & references<path-from-dist-root>[!/<entry-in-archive>]*

web/console.war!/WEB-INF/lib/nested.jar!/META-INF/sbom.cdx.json

The ! separates each archive from the path inside it — and nests for archives within archives. Open the WAR as a ZIP, open the inner JAR, read the SBOM.

Component referencing its own SBOM{
  "name": "admin-console",
  "purl": "pkg:maven/com.example/admin-console@2.0.0?type=war",
  "externalReferences": [
    {
      "type": "bom",
      "url":  "web/admin-console.war!/META-INF/sbom.cdx.json"
    }
  ]
}
Scanner
SHOULD resolve local refs; components in the referenced SBOM belong to the parent component. Remote URLs MAY be skipped.

§5.2 When one CPE isn't enough

Multi-product runtimes break the simple model

A Quarkus application bundles components from several products at once — each with its own CPE and VEX stream.

Which component belongs to whom?metadata.component → "my-quarkus-app"  (the app)

components:
  quarkus-core        → Quarkus product (own CPE)
  my-service          → the customer's app code
  jackson-databind    → 3rd-party, maybe many VEX streams

The top-level metadata.component names the deployed app — but the components below it belong to different products.

The problem: without knowing which component belongs to which product, a scanner can't route each one to the correct VEX/CVE source. A single product CPE no longer covers the SBOM.

What's needed is component-to-product attribution — the subject of the next slide.

§5.3 Component-to-Product Attribution · active implementation

Attribution via the dependency graph

Each upstream product is modeled as a framework component carrying its CPE; membership is expressed through provides edges. Native CycloneDX fields, no component duplication.

app (root · metadata.component — the customer's product) | +-- dependsOn --> pkg:maven artifacts (scope: required) | +-- dependsOn --> member product (CPE · framework · scope: excluded) | +-- provides --> attributed subset of artifacts
  • 1

    App is the root

    A product in its own right — no upstream CPE.

  • 2

    Members carry CPEs

    Non-root framework nodes, scope: excluded — reachable but flagged as non-runtime.

  • 3

    Shared artifacts, no dup

    Appear in multiple members' provides lists — one canonical bom-ref.

Member product + provides edge"components": [{
  "type": "framework",
  "bom-ref": "pkg:maven/…/quarkus-camel-bom@3.15.1.redhat-00001?type=pom",
  "purl":    "pkg:maven/…/quarkus-camel-bom@3.15.1.redhat-00001?type=pom",
  "cpe":   "cpe:2.3:a:redhat:camel_quarkus:3.15.1:*:…",
  "scope": "excluded",
  "evidence": { "identity": [
    { "field": "cpe", "concludedValue": "cpe:2.3:a:redhat:camel_quarkus:…" }
  ] }
}]
"dependencies": [
  { "ref": "…/my-quarkus-app@1.0.0",
    "dependsOn": [ "…/camel-quarkus-atom@3.15.1",
                  "…/quarkus-camel-bom@…?type=pom" ] },
  { "ref": "…/quarkus-camel-bom@…?type=pom",
    "provides": [ "…/camel-quarkus-atom@3.15.1" ] }
]
Role rules: Generator MUST model members as excluded framework+CPE and add provides edges. Scanner MUST follow provides to pick the right VEX stream; SHOULD evaluate shared components against all streams.
Open questions: the semantic fit of provides (canonical meaning is "implements a spec"); and whether the consumer (Trustify) keys attribution off component.cpe / evidence.identity vs. the RH CPE-as-bom-ref convention emitted by generators like SBOMer.
